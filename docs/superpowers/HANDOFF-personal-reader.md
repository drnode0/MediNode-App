# HANDOFF: 個人・部署ページのアプリ内リーダー（降格式）

作成: 2026-08-12／前セッション: クイズ穴埋め化・⚡展開（記憶: medinode-quiz-cloze-design / medinode-recap-standard）
**起動場所: ~/medical-search-public（このリポジトリ）。実装は最初からworktreeで**（別セッションのcheckoutで足元が変わる事故の再発防止）。

## ゴール

**tatsukiが自分の個人DB・部署DBで試しに使えるレベル**のアプリ内リーダー。GA品質・全ユーザー公開の磨きは求めない（フラグで自分だけに出せれば十分。EARLY_ACCESS_EMAILSの前例あり）。

動機: クイズ・今日の1問→「本文を読む」で個人・部署ページだけNotionアプリへ飛ばされ、毎日ループが途切れる＋プレミアムと導線が非対称。

## 価値観（設計の成立条件・オーナー確定）

**「どう書けば綺麗に表示されるか」を教えなくて済むことを成立条件にする。** 書き方の教育・指定・ガイドは一切作らない（オーナーの言葉:「より私だけの使い方を強制させる感じが出てしまったら嫌」）。そのための3原則:

1. **どんな書き方でも壊れない**: 描けるブロックは描き、描けないブロックは「このブロックはNotionで表示 →」の正直なプレースホルダ。最悪ケース＝一部読めて続きはNotionへワンタップ＝今より悪くなるページが存在しない
2. **読みにくいページに押し付けない**: 未対応ブロック比率が高いページはリーダー冒頭に小さく「このページはNotionの方が読みやすそうです → 開く」。判定は自動・無言。「あなたの書き方が悪い」というシグナルを出さない
3. **逃げ道常設**: リーダー内に「Notionで開く」を常に置く

## スコープ

### Phase 0｜計測の仕込み（意見の代わりにデータ）

- **ブロックタイプ分布**: /api/sync は既にクイズ候補ページの本文ブロックを取得している（cloze-sync.ts）。そこでtype別の出現数を集計し、/adminに「未対応ブロックの出現頻度」を出す→対応ブロック追加の優先度をデータで決める
- **「Notionで開く」タップ計測**: クイズ・今日の1問からの離脱回数＝この機能の需要の数値化。recordCqView（cq-views.ts）の実装パターンが参考になる

### Phase 1｜降格式リーダー本体

- 対象: owner が personal / team のページ。入口はまずクイズカード・今日の1問の「本文を読む」（現在は isInAppReaderTarget が subscription 限定 → 拡張）。検索カード（ResultCard）は動けば同時でよいが必須ではない
- 描画: 既存の描画器を流用（reader-doc.ts＝見出し1〜3・段落・箇条書き・番号リスト・callout・引用・区切り線・表・画像／ReaderBody.tsx＝annotations色対応済み）。未対応type（トグル・カラム・ページ内DB・埋め込み・数式・コード・同期ブロック等）はプレースホルダブロックとして描画
- 本文取得: 新APIルート（例 /api/personal/page）。**ユーザー自身のNotionトークンで取得**。トークンの受け渡しは /api/notion/search と /api/sync がどう受け取っているかを実装前に確認して踏襲する（クライアントから都度渡す方式か、サーバー保存の復号か——ここは前セッションで未確認）
- 画像: NotionのファイルURLは失効する。サブスク用の /api/subscription/image プロキシと同じ仕組みの個人版が要る（認可は「リクエストしたユーザー自身のトークンで取れる画像だけ」）
- 部署ページ: 部署トークンで同じ扱い。書き手が複数なので降格頻度は高い想定＝プレースホルダの見た目がここで一番試される

## やらないこと

- 全ブロック対応（終わりのない尻尾。分布データを見てから優先度づけ）
- 書き方ガイド・テンプレ推奨・「綺麗に表示されるコツ」の類いっさい
- サブスクリーダーの挙動変更（防衛目的の完全表示はそのまま）

## 使える資産と落とし穴（前セッションの実測）

- リーダーProvider: useReader() はProvider無しでもno-opで安全（SubscriptionReader.tsx:31）
- isInAppReaderTarget（subscription-open.ts）が「アプリ内で開くか」の唯一のゲート。ここを owner別に拡張するのが本丸
- reader-prefetch の先読みパターンをそのまま流用できる
- devハーネスの流儀: /dev/cloze・/dev/vine（development限定・notFound()ゲート・実データに触れない）
- vitestは .worktrees 除外設定済み。テストはNode環境（localStorageはvi.stubGlobalでモック＝personal-data.test.tsの方式）
- 個人用のlocalStorageキーを新設したら必ず PERSONAL_DEVICE_KEYS へ登録（アカウント切替の漏れ防止）
- sync系の手動実行: 本番のSUBSCRIPTION_SYNC_SECRETはローカルと不一致（401）。ローカルからtsxで直呼びする手順が medinode-knowledge-promote スキル仕上げ節にある
- デプロイはmainへpush＝Vercel自動。コミット前にブランチ確認

## 検証（完了の定義）

1. tatsuki自身の個人DBのナレッジをクイズ→「本文を読む」でアプリ内表示できる（見出し・箇条書き・callout・表・画像が出る）
2. トグルやページ内DBを含むページでプレースホルダが上品に出て、「Notionで開く」で逃げられる
3. 部署ページでも同様
4. /adminにブロックタイプ分布と「Notionで開く」タップ数が出る
5. 既存テスト全緑＋next build成功。公開はフラグ（自分のみ）でよい

## 進め方の提案

Phase 0 → Phase 1 の順。Phase 0 だけでも独立で価値がある（データが「作らなくていい」と言うならそれも成果）。設計相談の経緯は本ファイルの価値観節が正——迷ったら「教育ゼロで成立するか」で判断する。
