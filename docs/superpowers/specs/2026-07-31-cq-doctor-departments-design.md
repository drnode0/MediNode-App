# 臨床疑問フォーム：医師の「診療科・立場」を受け取る（2026-07-31）

## 背景

同日デプロイした [職種・経験年数の必須化](2026-07-31-cq-required-fields-design.md) で、
アプリ内のCQ投稿から職種が必ず取れるようになった。しかし職種リストの `医師` は1つしかなく、
**初期研修医なのか集中治療科の指導医なのかが区別できない**。この差は回答の前提を大きく変える。

受付DB `❓ MediNode 臨床疑問受付_DB` には既に `診療科・立場`（multi_select）という列があり、
外部Notionフォームは医師のときだけ条件表示で訊いている（フォーム上は任意）。

```
初期研修医 / 専攻医（専門研修中） / 指導医・専門医 /
救急科 / 集中治療科 / 麻酔科 / その他の診療科
```

アプリはこの列をまったく扱っていない（`buildIntakeProperties` に登場しない）。
**外部フォームでは解けている問題が、アプリだけ抜けている**状態。

## スコープ

アプリ内フォームのみ。Notion側は列も選択肢も既存のものをそのまま使うので**変更ゼロ**。
外部Notionフォームの設定（任意のまま）も変更しない。

### 不変条件

1. 追加項目が出るのは「専門医に訊く」を届け先に選び、**かつ職種が `医師` のとき**だけ。
   他の職種を選んでいる人には一切見えない。
2. 「自分のメモ」だけに送る動作は疑問文1つで送れるまま変えない。
3. 受付DBに `診療科・立場` 列が無くても投稿自体は失敗させない
   （`buildIntakeProperties` の既存方針）。

## 1. 何を訊くか

正となる選択肢は受付DBの `診療科・立場` の7つ。**アプリ側で選択肢を増やさない**:

```
初期研修医 / 専攻医（専門研修中） / 指導医・専門医 /
救急科 / 集中治療科 / 麻酔科 / その他の診療科
```

複数選択可・**1つ以上で必須**（外部フォームは任意だが、アプリでは必須にする。
今回「任意と書けば書かれない」ことが実データで裏づけられたため）。

UIは `<select multiple>` ではなく**トグルチップ**にする。スマホで複数選択の select は
扱いづらく、また届け先チップという同じ操作感が既にモーダル内にあるため。

## 2. 職種を切り替えたときに診療科を捨てる

医師で `救急科` を選んだあと職種を `看護師` に変えたら、選択済みの診療科は**捨てる**。
残すと看護師の投稿に救急科が付いたまま届く。

同日の「続けて残す」で背景が次の疑問に持ち越された不具合と同じ型の事故なので、
職種の `onChange` で明示的に空にする。UIが隠れるだけでは足りない。

## 3. 検証

サーバー（`validateCqSubmission`）:

- 職種が `医師` のとき: `departments` が空なら `診療科・立場を選択してください`。
  リスト外の値が1つでもあれば `診療科・立場はリストから選択してください`。
- 職種が `医師` 以外のとき: `departments` は**空配列に正規化**する（エラーにしない）。
  クライアントが何を送ってきてもサーバーで捨てる、という形にして
  「看護師なのに救急科が入っている」行が受付DBに生まれる経路を塞ぐ。
- 配列でない値（文字列・null 等）が来たら空配列として扱う。
- 重複は取り除く。チップUIからは重複しないが、入力は信用しない
  （同じ値が並んだ multi_select を受付DBに書かないため）。

UI:

- 送信時に未選択なら `診療科・立場を選択してください` を出し、**チップ群の先頭のチップ**へ
  フォーカスを返す（チップは `<button>` なのでフォーカスできる）。
  既存の職種・経験年数と同じ流儀（送信ボタンは disabled にしない）。

`buildIntakeProperties`:

- `departments` が空でなく `schema['診療科・立場']?.type === 'multi_select'` のときだけ
  `{ multi_select: [{ name }, ...] }` を積む。空のときは列ごと積まない
  （既存値を空で上書きしない、という既存方針に揃える）。

## 4. 端末への記憶

`CqProfile` に `departments: string[]` を追加し、職種・経験年数と同じく端末に記憶する。
読み込み時に確定リストに無い値は落とす（同日入れた職種の移行処理と同じ考え方）。

## 5. あえて残す重複

`初期研修医 / 専攻医（専門研修中） / 指導医・専門医` は経験年数（`1年目` `2〜3年目` …）と
かなり重なる。それでも分けないのは2つの理由による:

1. 外部フォームと選択肢を揃え、受付DBの `診療科・立場` 列の集計を一本化するため
2. 年数だけでは「4〜6年目の専攻医」と「4〜6年目だが既に指導医」が区別できないため

## 6. 検証（テスト）

純ロジックは `src/lib/cq-submit.ts` に寄せ、`src/lib/__tests__/cq-submit.test.ts` で検証する:

- 職種が `医師` で `departments` が空 → 拒否
- 職種が `医師` でリスト内の値が1つ以上 → 通る
- 職種が `医師` でリスト外の値が混ざる → 拒否
- 職種が `看護師` で `departments` に値がある → 通る、かつ `departments` は `[]` に正規化される
- `departments` が配列でない → `[]` として扱う
- `buildIntakeProperties` が `診療科・立場`（multi_select）に積む／空なら積まない／
  列が無ければ黙って飛ばす

UIは自動テストなし（既存方針）。`npx tsc --noEmit` と `npm test` と `npm run build` で確認する。

## やらないこと

- 外部Notionフォームの変更（任意のままにする。フォーム側は既に訊けている）
- Notion受付DBのスキーマ変更（列も選択肢も既存のものをそのまま使う）
- 医師以外の職種の内訳（看護師のICU／病棟／救急外来など）。今回の起点は医師の粒度であり、
  他職種に広げるかは実データを見てから判断する
- 受付DBに既にある `診療科・立場` の値の移行や整理（追加で書き込むだけ）
