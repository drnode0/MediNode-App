# 臨床疑問フォーム：職種・経験年数の必須化と背景のソフト必須（2026-07-31）

## 背景

アプリ内の臨床疑問（CQ）投稿で、疑問文（タイトル）だけを送る投稿が続いている。
背景・状況が無い疑問は「答えられる疑問」にならず、作者のトリアージで止まる。

現状を実データで確認した（受付DB `❓ MediNode 臨床疑問受付_DB`、全17件、2026-07-31時点）:

| 投稿経路 | 件数 | 背景が空 | 職種が空 | 経験年数が空 |
|---|---|---|---|---|
| アプリ内 | 2 | 2 | 2 | 2 |
| 作者 | 14 | 0 | 0 | 14 |
| （未設定・フォーム由来と思われる） | 1 | 0 | 0 | 0 |

母数は小さいが、アプリ内投稿は2件とも全欄が空。

原因は明確で、**外部Notionフォームは既に 疑問／背景・状況／ご職種／経験年数／掲載名の希望 を
すべて必須にしているのに、アプリ内フォームだけが全部「（任意）」になっている**。
アプリ内投稿を実装した際に「入力の負担を増やして投稿自体を止めない」方針を採ったが、
実際には記入されないまま届いている。

あわせて、調査中に既存の不具合を1件見つけた（下記 3 章）。

## スコープ

対象は**アプリ内フォームのみ**。外部Notionフォームの必須設定は既に正しいので変更しない。

### 不変条件（壊してはいけないもの）

1. 必須が効くのは**「専門医に訊く」を届け先に選んだときだけ**。
   「自分のメモ」だけに送る従来動作は、疑問文1つで送れるまま変えない
   （詳細パネルは `dest.expert` が false なら描画すらされない）。
2. 職種・経験年数・ペンネームは端末に記憶される（`medinode_cq_profile_v1`）。
   したがって必須化が壁になるのは**初回投稿の1回だけ**で、2回目以降は既に埋まった状態で開く。
3. 受付DBに該当プロパティが無くても投稿自体は失敗させない（`buildIntakeProperties` の既存方針）。

## 1. 職種・経験年数をハード必須にする

対象: `src/components/CqCapture.tsx` の詳細パネル、`src/lib/cq-submit.ts` の検証。

- ラベル: `職種（任意）` → `職種` ＋必須マーク、`経験年数（任意）` → 同様。
  select の先頭 option を `職種を選択` / `経験年数を選択` に変更（現在は `職種（任意）`）。
- **送信ボタンは disabled にしない。** 現在の disabled 条件
  （`saving || !title.trim() || (!willSendMine && !willSendExpert)`）は変えず、
  押下時に検証して未入力欄にエラー文とフォーカスを当てる。
  disabled にすると「なぜ押せないか」が伝わらないため。
- 検証は `willSendExpert` が true のときだけ走る。エラーは既存の `expertError` に流す
  （「専門医への投稿: …」の接頭辞が付く既存表示に乗る）。
- サーバー側 `validateCqSubmission` でも必須にする:
  - `occupation` が空 → `職種を選択してください`
  - `experience` が空 → `経験年数を選択してください`
  - 空でない場合のリスト検証は現状のまま。
- 背景はサーバー側では**任意のまま**。ソフト必須はUIの責務とする（2章）。

### 既知のトレードオフ

Service Worker のキャッシュで古いJSを持っている端末が空のまま投稿すると、
サーバー側の必須化により 400 が返る。日本語のエラーメッセージがモーダルに出るため
致命的ではなく、再訪時に新しいJSへ更新される。許容する。

## 2. 背景・状況をソフト必須にする

対象: `src/components/CqCapture.tsx`。

- ラベルから「（任意）」を外す。補足文は
  「空でも送れますが、あると回答の精度が変わります」に。
- 背景が空のまま送信を押したとき、**送信せず**に背景欄の直下へインライン確認を出す
  （モーダルは重ねない。reader上に重なって開く構造のため、これ以上の重ね掛けはしない）:

  > 背景が空のままです。どんな場面で・何を試して・何に迷っているかが一言あると、
  > 答えられる疑問になります。
  >
  > `背景を書く`（背景欄へフォーカス） / `このまま送る`

- `このまま送る` を押すと確認済みフラグが立ち、そのまま送信される。
  以後、そのモーダルが開いている間は再確認しない。
- 確認が出ている間は送信全体を止める（メモ側も送らない）。ユーザーが選択したあとに
  両方の届け先へまとめて送る。`handleSend` の並列送信構造は変えない。

## 3. 受付DBの職種列を「職種」に一本化する

### 見つかった不具合

受付DBには職種列が2本ある:

- `職種`（select・15選択肢）… 外部Notionフォームが書き込む。フォーム上は必須。
- `投稿者職種`（select・13選択肢）… アプリ内投稿が書き込む。

受付DBを直接読んでいるコードは `src/lib/cq-board.ts`（みんなの臨床疑問ボード）だけで、
これは `投稿者職種` しか読まない。そのため**外部フォーム経由の投稿はボードで職種バッジが出ない**。
実データでも `職種=看護師 / 投稿者職種=空` の行が1件あり、この行の職種は表示されていない。

紛らわしいので明記しておく（調査の結果、以下は受付DBとは無関係）:

- `src/app/api/subscription/sync/_core.ts` の `props['投稿者職種']` は
  **Medical Knowledge_DB（サブスク用）の同名プロパティ**であり、作者が手で入力する。
  選択肢も別物（`医学生 / 研修医 / 医師（救急・集中治療に関わる全科） / …` の14個）で、
  そちらに `職種` 列は存在しない。**このファイルは変更しない。**
- `src/lib/resolved-cqs.ts` は Algolia レコードの `posterRole` フィールドを読むだけで、
  Notionのプロパティ名には触れない。**このファイルも変更しない。**

### 対応

正となる選択肢を受付DBの `職種` 側（15個）に寄せる。ただし2点だけ調整する。
どちらも該当データ0件のため安全:

- Notion側: `医学生` → **`学生（医学生・看護学生など）`** にリネーム。
  現在アプリ側にある「学生」を吸収し、看護学生・薬学生の行き場がない現状のギャップも埋める。
- アプリ側: `管理栄養士` → `管理栄養士・栄養士`（Notion側の表記に合わせる）。

確定する選択肢リスト（`CQ_OCCUPATIONS` を差し替え。並び順はアプリの表示順であり、
Notion側の option 順とは独立でよい）:

```
医師 / 看護師 / 保健師・助産師 / 薬剤師 / 管理栄養士・栄養士 /
臨床工学技士 / 診療放射線技師 / 臨床検査技師 /
理学療法士 / 作業療法士 / 言語聴覚士 / 救急救命士 /
学生（医学生・看護学生など） / その他医療従事者 / その他
```

書き込みと読み取り:

- `buildIntakeProperties`: `職種` が select なら `職種` に書く。
  `職種` が無く `投稿者職種` がある受付DBでは旧列に書く（フォールバック）。
  両方ある場合は `職種` のみに書き、`投稿者職種` は書かない。
- `src/lib/cq-board.ts` を「`職種` → 空なら `投稿者職種`」の順で読むよう変更（変更はこの1ファイルのみ）。
- 受付DBの `投稿者職種` はレガシーな読み取り専用列として残す（過去のアプリ内投稿2件を拾うため）。

### 端末に残る旧プロフィールの扱い

`loadCqProfile()` で読んだ `occupation` が新リストに無い値なら空文字に落とし、再選択させる。
（旧値 `学生` `管理栄養士` が対象。実データ上、該当ユーザーは0人。）

## 4. 検証

- `src/lib/__tests__/cq-submit.test.ts`
  - 職種が空 → エラー、経験年数が空 → エラー
  - 新リストの値が通る／リスト外は拒否
  - `buildIntakeProperties` が `職種` に書く／`職種` が無ければ `投稿者職種` に書く／
    両方あれば `職種` だけに書く
- `src/lib/__tests__/cq-board.test.ts`
  - `職種` のみの行、`投稿者職種` のみの行、両方ある行で正しい職種が読める
- 型チェックとビルドが通ること。

## 5. 作業ブランチ

`feat/cq-required-fields`（main へ直接コミットしない）。

Notion側の選択肢リネーム（`医学生` → `学生（医学生・看護学生など）`）は
コードのデプロイ前に済ませておく。順序が逆だと、リネーム前の受付DBに
新しい選択肢名で書き込まれ、option が自動生成されて重複する。

## やらないこと

- 外部Notionフォームの変更（既に必要な項目はすべて必須）。
- 掲載名の希望・診療科・立場のアプリ内対応（外部フォームのみの項目のまま）。
- 投稿後に背景を追記させるフォローアップ動線。
- 受付DBの `投稿者職種` 列の削除やデータ移行（読み取りフォールバックで足りる）。
