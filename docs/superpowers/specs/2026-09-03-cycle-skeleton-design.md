# 双輪サイクルの骨組み（部品の並び・継ぎ目・回し方）

日付: 2026-09-03
状態: オーナー承認済み（会話で段階確認。案「1周を先に通す」を採用）。各部品の実装計画は部品ごとに別セッションで起こす
先行資料:
- 外の輪 `docs/superpowers/specs/2026-09-02-outer-wheel-design.md`（段0／段1／段2の契約）
- 内の輪 `docs/superpowers/specs/2026-09-02-recall-engine-design.md`（主張・球・確かめる・SRS・テーブル・今日の1問の撤去範囲）
- 双輪の骨格（2026-09-01。正は Notion 🎬プロジェクト_DB「MediNode アプリ開発」配下）

## 背景・課題

内の輪（Recall）は実装が本番に入り、外の輪は設計が承認された。しかし両輪を「一周」として回した人はまだいない。
コードの現物を辿ると、輪は次の箇所で途切れている（2026-09-03 に読み取り専用で確認）。

外の輪（疑問 → 正本）
- 疑問の入口が3つに割れ、返るものが違う。検索はページ着地で終わり、投げ込みは「届きました」で待ち、
  節末の「気になる」は票数だけを返す。段0（棚を引く）は未実装
- 作者側の操作（「対応済み」への変更・ボード公開・「気になる」の集計の目視）はすべて Notion 手作業で、
  アプリは受付DBを読むだけ。書き戻す API が無い
- 正本になった事実がアプリへ戻る経路は、未コミットの通知 cron（`cq-answer-notify`）だけ。
  「依頼者には最初から残した状態で入る」接続点は未実装で、受付DBの行と `recall_claims` を結ぶ列が無い
- 送った疑問の追跡がサーバー側（`cq-mine`）と端末側（`cq-dispatch`）の二重

内の輪（読む → 残す → 確かめる → 定着）
- 読む画面に「残す」が無い。確信度マーク（`ConfidenceMark`）はアイコンだけで押せず、「残す」は球の閲覧カードに閉じている
- 節の読了 API（`/api/recall/read`）に呼び手が無い。「読んだ」の光は一度も点かない
- 残した主張は利用者の Notion に落ちない（設計未着手）。ただし利用者のトークンで DB を新規作成する
  API（`/api/notion/create-db`）が既にあり、OAuth の権限も読み取り＋挿入まで持つ
- クイズタブ（端末保存・赤マーカー母集団）と今日の1問が Recall と並存している

制作工程との接点
- 段2の依頼は受付DBに入るが、正本化した主張を依頼に結ぶ列が無い

本設計は、これらを閉じる部品の並びと、どの部品も勝手に決めてはいけない継ぎ目を固定する。
部品の中身の設計は、必要な部品だけ別セッションで行う。

## 用語

- **主張／残す／読んだ／確かめる／定着**: Recall 設計の定義に従う
- **段0／段1／段2**: 外の輪の設計に従う（棚を引く／AI に組ませる／作者に検証を依頼）
- **正本化**: 依頼された問いが制作工程を経て公開ページの主張になること
- **部品**: 1セッションで設計または実装する単位。本設計では 0〜8 の9個（8 はパーツ調査で追加）
- **継ぎ目**: 複数の部品が同じものを読み書きする箇所。本設計で固定し、部品の設計で変えない

## 目的と成功条件

**目的**: 双輪サイクルを、オーナー1人が本番で一周できる状態にする。すべて先行体験のフラグ（`recall`・`ask_shelf`）の内側で行う。

**成功条件**（オーナーが本番で実測して判定する）

- 内の輪: 記事を読む → 主張行で「残す」→ 球で光る → 翌日「確かめる」→ 覚えた／まだ → 記録が Supabase に残り、
  自分の Notion の DB に主張が1行入る
- 外の輪: 疑問を書く → 段0が主張を返す（無ければ「棚に無い」の1行）→ 依頼 → 受付DBに段0の結果つきで入る →
  オーナーが制作工程で正本化 → サブスク同期で主張が入る → 依頼者にメールが届き、その主張が「残した」状態で球に灯る
- 段1: ボタンで AI 回答が返り、未検証の表示と引用チップが出て、MediNode 側に保存される

**非目標**

- 一般公開（drnode.com の公開判断まで先行体験の内側）
- 見た目の方向の決定（部品3の後に、現行維持と Node Field 寄せを並べて決める。それまでは現行の写しに合わせる）
- クイズタブと Recall の統合（部品6で判断だけ行う）
- 個人・部署ナレッジの主張を球に出すこと（v2）
- 制作スキル（CQ・Essentials・検証層）の中身の変更。本設計が触るのは受付DBの列という接点だけ

## 完成形の体験（オーナー専用の状態で回す1週間）

1. **現場で3秒。** 検索タブの窓に疑問を自然文で書く。上に段0の主張が数件（各行に「残す」と「この節を読む」）、
   下に今までどおりのページ。主張が無ければ「この問いそのものの主張はまだ棚に無い」の1行と近い主張、
   その下に「作者に検証を依頼」と「AI に組ませる（未検証）」
2. **依頼。** 受付DBに「段0結果」つきで入る。受付画面に「票の多い順に、月に数件を正本にします」の1行が出る
3. **閲読。** 主張行の右端の「残す」、節末の「この節を読んだ」。残した行は翌朝、自分の Notion の DB に入っている
4. **確かめる。** 球の「確かめる」で期限の来た主張が最大5枚。伏せ字カードか想起カード。裏は原文と出典
5. **正本が戻る。** 制作工程で正本化 → 同期 → 依頼者にメール。球にはその主張が「残した」で灯るが、
   期限は依頼者が初めて開いた時点から始まる（初見をクイズにしない）
6. **週1の便り。** 「今週確かめる主張が n 件」と傾向1行（「まだ」が多い区画、棚にあって自分が触れていない区画）

一般の利用者は、この期間は今日と同じ画面（フラグの外側）。今日の1問だけが部品6で消える。

順番の根拠
- 0 は以後の全部品が見た目の基準にするので最初
- 1 と 2 は土台が既にあり、一周の両端を先に繋ぐ
- 3 は正本の紐づけ（受付DBと主張の対応）を決める部品で、4 より前に置かないと、先に残した記録を付け替えることになる
- 5 は費用の実測が要るので、3 で疑問の流れが通ってから乗せる
- 6 は 1〜3 をオーナーが一周した後。撤去だけを先にすると、内の輪を外から引くものが無い期間ができる
- 7 は読む画面の部品を 1 が先に触るので後。2026-08-12 の判断（要点モードは個人ページに出さない・書き方の教育をしない）を
  一部開け直すため、/admin に貯まる計測（ブロック分布・離脱タップ）を見てから設計する
- 8 は同期側（主張の ID が変わる検出）と出典台帳側（撤回・改訂の検出）の両方に触るので、3 の後。実際に改訂が1件起きたときを目安にする

### 各部品の要点

**部品0 `DESIGN.md`**
- 置き場はリポジトリ直下。中身は現行のトークンの写しであり、新しい見た目を決めない
- 実装セッションはこれを読んでから画面を足す

**部品1 読む画面の「残す」と「読んだ」**
- 対象はサブスクのアプリ内リーダー（`ReaderBody` と `ReaderSpread`）。個人・部署ページには置かない（v1 の主張はサブスク限定）
- 「残す」を置く行は、主張抽出（`extract-claims.ts` の `splitClaim`）が主張と判定する行だけ。判定は共有の純関数を使い、
  行の本文から `claimIdOf(ページID, 本文)` を計算して `/api/recall/claims` の一覧と突き合わせる。
  一覧に無い行（未同期・除外対象）には置かない
- 「この節を読んだ」は節末の明示ボタン。節の番号は主張抽出と同じ規則（番号付き H2 → `sec{n}`）。
  スクロールでの自動判定はしない（Essentials 1本で71件が「読んだ」になるのを避ける）
- 既存の端末ローカルの読了水位（`ReaderMarksProvider`。続きから読むための位置）は別物として残し、統合しない
- 「残す」に一括操作を置かない（後述の継ぎ目）
- `hasFeature('recall')` が偽の利用者には、ボタンも節末の操作も描かない

**部品2 回答通知の仕上げ**
- 実装済み。`vercel.json` の cron（`/api/cron/cq-answer-notify`）と `cq-mine` の「対応済み」判定を含めてコミットし、
  本番で `CRON_SECRET` 付きで1回手動実行して `mailed` の件数を見る
- 部品3で「正本主張ID」列が入るまでは、メールだけを送る（従来の振る舞い）

**部品3 聞ける棚の段0と段2**（設計セッションで決めること）
- 段0の検索方式（埋め込みの種類・日本語全文検索との併用・更新頻度）。列は `recall_claims` に足す
- 「正本主張ID」を誰が書くか（管理画面の操作か、Notion での手入力か）
- 依頼の受付画面の期待値の文言と、「対応不要」になったときの理由の見せ方
- 空白候補ビュー（受付DBの1ビュー。段0結果＝該当なしで絞る）
- **制作工程との受け渡し**: CQ スキル（`medinode-cq-note`）が受付DBの依頼を入口として読む手順と、正本化したときに
  「対応状態＝対応済み」と「正本主張ID」を書き戻す手順。スキルの中身は変えず、入口と出口の2手順だけを決める
- **音声で疑問を入れる**: 検索タブの窓に音声入力を置くか。置くなら、AI が整えるのは疑問文の形だけで、答えは作らせない
- **訂正の種別**: 依頼に「この問いの主張が棚に無い」だけでなく「この主張は違う」を主張ごとに投げられる入口を置く。受付DBの種別列（既存の列で足りるか）と、部品8の改訂の旗への繋ぎを決める

**部品4 Notion への一方向落とし**（設計セッションで決めること）
- DB の自動作成の流れ（既存の `/api/notion/create-db` の流用範囲）と、作成済み DB の ID の保存先（`user_settings` の暗号化設定）
- 書き込みのタイミング（残した直後か、まとめてか）と失敗時の再送
- Notion API の世代（現行の 2022-06-28 固定のままか、2025-09-03 版へ上げるか）。参照実装は SUBSCreen

**部品5 段1**（設計セッションで決めること）
- モデルの選定と費用の記録。表示規約（未検証・引用チップ・由来なし）。保存先のテーブル
- 費用方式の候補: 1日 n 回まで無料にして残り回数を表示する（Pocket-ER の型）。実測後に決める

**部品6 今日の1問の撤去と週1の便り**
- 撤去範囲は Recall 設計書「今日の1問の撤去範囲」の表のとおり
- 週1の便りは既存のプッシュ基盤（`push_subscriptions`・`push_notify_prefs`）で送る。日次にしない。
  中身は「今週確かめる主張が n 件」と傾向1行。傾向は `recall_review_log`・`recall_progress`・`recall_section_reads` と
  `recall_claims` から計算だけで出す（AI の作文は使わない）
- 傾向で出してよいもの: 区画ごとの「まだ」の率、残した主張の区画の偏り、読んだが残していない節、
  棚にあって自分が一度も触れていない区画。出してはいけないもの: 点数・順位・赤い表示・未解決の数を責める文言
- クイズタブの端末記録（`quiz-srs.ts`・localStorage）を Recall へ移すか捨てるかは、ここで判断する

**部品7 自分のナレッジの入口と出口（記載フォーム＋昇格描画）**（設計セッションで決めること）
- 書く側（記載フォーム）: 利用者が MediNode に適した書き方を自分で覚えなくても済むように、アプリ内のフォームに入力すると
  テンプレ規約どおりのブロックが利用者の Notion DB に書かれ、同じ原本がアプリ内にも描かれる。
  他の AI（ChatGPT など）で得た回答の保存先にもなる（流れていく回答を止める入口）
- フォームの AI 補助は「形を整える」だけに限る。URL を貼れば要約、スクリーンショットを貼れば文字起こし、画像は整形。
  **答えを作らせない。補助で入った文は既定で ❓（未検証）とし、✅ にできるのは出典を伴う行だけ**。
  検証済みのサブスクと同じ見え方で描くからこそ、未検証の行が同じ確信度に見えてはいけない
- v1 はページの新規作成のみ（既存ページの編集は Notion 側で行う。OAuth の権限は読み取り＋挿入まで確認済み、更新は未確認）
- 既存の土台: `/api/notion/create-cq`（利用者のトークンで自分の DB にページを作る）、`/api/notion/create-db`、
  複製テンプレ（設定の `notionDuplicatedTemplateId`）。CQ Catcher（別アプリ）の捕捉経路と役割が重ならないよう、設計で線を引く
- 読む側: 既存の降格式リーダー（`isInAppReaderTarget`・`/api/personal/page`）を既定のまま残し、テンプレ規約に沿うページだけ昇格させる。
  昇格の判定と、昇格したときの見え方（スプレッドとの共通部品）
- 配るテンプレ（複製元）の更新。教育はしない。フォームが規約どおりに書くので、教育の代わりになる
- AI 補助の費用と、画像の Notion への保存方法（ファイルアップロード API の可否）は設計で確かめる（未確認）

**部品8 改訂の旗（鮮度）**（設計セッションで決めること）
- 内の輪の骨格の5段目「鮮度（改訂で旗）」を担う。主張の本文が改訂されると ID が変わり旧 ID は `active=false` になるが、
  それを残していた人には何も届かないのが現状
- 決めること: 旧 ID と新 ID の対応の取り方（同じページ・同じ節・近い本文）、残していた人への旗の見せ方（球の色か印か）、
  カードの差し替えと SRS の記録（段・間隔）の引き継ぎ、出典台帳側で原著の撤回・懸念表明・改訂版を拾う口
- 参考の型: AnkiHub（承認制で全購読者へ自動配布）、scite Reference Check（撤回・懸念表明の通知）

## 今の時点で固定する継ぎ目

1. **主張の鍵は1つ。** `claimIdOf(ページID, 本文)`（sha1 先頭24文字。`extract-claims.ts` に実装済み）。
   受付DBの紐づけ列、Notion に落とす行の「MediNode ID」、段0の検索結果、すべてこの値を使う。
   他の部品が独自の ID を作らない。本文改訂で ID が変わる件は Recall 設計の `active=false` 方式に従う
2. **「残した」の記録は `recall_progress` の1本だけ。** 読む画面、球、段0の結果、依頼の正本化、どこから残しても同じ行。
   Notion への落としはこの表の変化を写す一方向
3. **「読んだ」は節ごとの明示操作。** `recall_section_reads` に `sec{n}` で記録する。
   既存の端末ローカルの読了水位とは統合しない
4. **受付DBに足す列は3つ。** 「段0結果」（select: 該当あり／該当なし／未実行）、「段0主張ID」、「正本主張ID」
   （どちらも rich_text。主張の鍵をカンマ区切り）。既存の列は変えない。
   列が無い受付DBでも既存動線が壊れないこと（`cq-submit` の `buildIntakeProperties` は無い列を積まない）
5. **正本化の合図は「対応状態＝対応済み」かつ「正本主張ID が空でない」。** 通知 cron がこの2つを見て、
   依頼者の `recall_progress` に「残した」を書き（`kept_at` は正本化の時刻、`due_at` は null）、メールを送る。
   **`due_at` は依頼者がその主張か節を初めて開いた時点で「間隔1日・期限翌日」に設定する**（初見をクイズにしない）。
   メールと球のタップ先は読む画面の該当節。正本主張ID が空なら従来どおりメールだけ。
   フラグが閉じている依頼者にも `recall_progress` は書いてよい（画面には出ない。開いたときに最初から灯る）。
   メール文面に Recall の名前を出さない
6. **機能フラグは `recall`（既存）と `ask_shelf`（新設）。** どちらも専用の許可メール（`RECALL_EMAILS`／`ASK_SHELF_EMAILS`）で、

### Recall セッションへの申し送り（球と確かめるの改良。骨組みの外）

- **明るさを「思い出せる確率」にする。** FSRS の保持率 R(t) = (1 + (19/9)·t/S)^(-1) を、S に現在の間隔日数を入れて計算する。段は固定のままで、状態層の式だけが変わる。
  離脱候補の閾値もこの値で引き直す。価値: 高
- **「覚えた／まだ」を3択にする案。** Readwise Mastery は soon（7日）／Later（14日）／Someday（28日）の3択で、すべて日数ラベル。自己採点の語彙を使わない。
  「もう一度／来週／しばらく先」の形なら選択肢式クイズとは無関係のまま情報量が増える。価値: 高
- **伏せ字の量を記憶度で変える。** 暗い主張は数値1つだけ、明るい主張は上限3まで。原文の伏せ方だけ変えるので AI 作成には当たらない（Monoxer の段階化。出題形式の記述は未確認）。価値: 高
- 1日最大5枚の上限を、内部の「目標保持率」1つのノブに置き換える案（Anki の Desired Retention、既定90%）。実測後。価値: 中
- FSRS を全面採用はしない。個人最適化には数百回以上のレビューが要り（Anki マニュアル）、読者1人ではそこに届かない。固定段には SM-2 のような病理が無く、置き換えの得が小さい

- OpenEvidence の EvidenceGrade（AI が根拠の強さを採点）。「信頼できる AI 検索」の売り方そのもので、競合調査の結論に反する
- 選択肢式と誤答の自動生成（Quizionary・Recall の選択形式）。却下済み
- 学習ヒートマップ・連続記録（Anki Review Heatmap・Screvi のストリーク）。却下済み
- 実名 Q&A（Antaa QA・ヒポクラ）。却下済み。借りるのは期待値の数と工程だけ
- Notion Forms。本文ブロックを作れない
- 「整理しない」思想の全部（mymind）。出典必須は崩さない。借りるのは分類を求めないことだけ

### 調査で確認した MediNode の独自性

主張1行を検索の単位にする製品は既にある（scite の Citation Statement Search、Consensus の抜き書き）。ただしそれらの1行は「論文にそう書いてあった」記録で、人が正しさを引き受けた主張ではない。
Doximity は人が引き受けるが1.2万人の集合で、誰が引き受けたかは特定できない。
MediNode の1行も論文から引いた記述で、行為としては同じである（オーナー自身の指摘、2026-09-03）。差は人が特別なことではなく、
**工程が見えること**にある。全行に出典、確信度の印、層2と層3の照合の来歴、訂正の履歴。scite の引用文は機械が拾い、誰も読んでいない。
MediNode の1行には誰かが読んで確かめた跡が残る。差はそこまでで、棚が小さいうちは細い差でもある。
だから旗は「確かめてある」ではなく「二度目は、調べなくていい」のままにし、段0では「無いときに生成で埋めず、棚に無いと言い切る」ことを守る。

個人開発アプリは、オーナーが X で見つけてブックマークしたものを定期的に拾う方法と併用する（NewMemo はその経路で見つかった）。
