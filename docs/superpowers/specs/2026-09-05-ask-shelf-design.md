## 決定事項

### 1. 段0は3層で返す（裁定2・更新案A）

上から「主張」→「節・記事」→「板に出ている近い疑問」。各層は独立して空になりうる。
3層とも空のときだけ、依頼だけが残る。

#### 層1 主張（`recall_claims`）

**方式: 文字2つずつの照合＋覆い率。埋め込みは使わない。**

- 主張の倉庫は増やさない（継ぎ目7a）。`recall_claims` に列を足す。
  - `keywords text not null default ''` … 同期のときにページのキーワード欄を写す
  - `search_text`（本文＋節見出し＋`keywords` の生成列）と PGroonga の索引は、
    **0030 とは別のファイル（0031、任意適用）にまとめて置く**。拡張が入っていない環境では
    `create index using pgroonga` 自体が失敗して 0030 ごと流れなくなるうえ、
    索引を入れない人には誰も読まない列が残るため。0030 だけ流せば段0は動く。
  - **PGroonga が有効でなければ全件を読んで同じ計算をする**フォールバックを持つ。
    687 行では体感差が無いため、Supabase の拡張の有効化を本番投入の前提条件にしない。
- 照合の正は **TypeScript の純関数**（`src/lib/ask-shelf/coverage.ts`）。
  文字 bigram に割り、コーパス全体の出現頻度から重みを付け（珍しい語ほど重く）、
  コーパスに1度も出ない語は最大の重みで扱う。
  **覆い率 = 問いの語の重みの合計のうち、その主張が持っている語の重みの割合。**
  PGroonga は候補を絞るためだけに使い、順位と足切りは常にこの純関数が決める。
  こうすることで、設計時の実測がそのまま本番の振る舞いになる。
- **足切りは覆い率 0.25。** 上位5件まで。
- 並びは覆い率の降順。ただし利用者自身が残した主張（`recall_progress` に有効な行がある）を
  最上位に置き、「あなたが残した」の印を付ける（継ぎ目7b）。
- 0件のときの1行は「**MediNodeにはこの問いの検証済みの主張はまだありません**」（更新案B）。
- 各主張に「残す」と「この節を読む」を置く（継ぎ目7c。主張を行き止まりにしない）。
  飛び先は読む画面の該当節（`section_key` の `sec{n}`）。

##### 実測（2026-09-05・本番 `recall_claims` 687 行）

問い38件を通した。棚にある側27件はサブスク記事の題名（＝臨床の疑問文）で、正解はそのページ由来の主張。
棚に無い側11件は、公開中の未解決の板に出ている5件と、コーパスに無い分野6件（小児・産科・制度・眼科・整形・精神）。

| 物差し | 正解が1位 | 上位5位 | 棚に無い問いを誤って出す |
|---|---|---|---|
| 点数（BM25）だけ | 81% | 96% | **切り分け不能**。棚に無い問いの最高点 36.6 が、棚にある問いの最低点 16.8 を上回る |
| 覆い率（本文＋節見出し＋キーワード） | 96% | 100% | **0 / 11** |

覆い率の分布は、棚にある側が中央値 0.40・最小 0.19、棚に無い側が中央値 0.15・最大 0.19。

| 閾値 | 棚にあるのに「無い」と言う | 棚に無いのに出す |
|---|---|---|
| 0.25 | 2 / 27 | 0 / 11 |
| 0.30 | 6 / 27 | 0 / 11 |
| 0.40 | 13 / 27 | 0 / 11 |

0.25 を採る。点数で切れない具体例として、「尿道カテーテルはいつ抜くべきか」（棚に無い）が
乏尿の記事の主張に 36.6 点を付ける。覆い率では 0.14 で、正しく「無い」になる。

**この実測の限界。** 棚にある側の問いは記事の題名なので、実際の利用者の言い回しより有利である。
本番では「無い」が実測より増える見込み。だから層2・層3が要る。主張の層は厳しく断ってよい。
閾値は定数として1か所に置き、`ask_shelf_queries` の記録を見て後から引き直せるようにする。

**埋め込みを採らない理由。** 上の精度が API キー・pgvector・検索ごとの費用なしで出ており、
かつ埋め込みでも「無い」と言う閾値は別に要る（コサイン類似度は水準がそろわない）。
再検討ライン: 主張が 2,000 を超えたとき、または覆い率 0.25 の取りこぼしが記録上 3割を超えたとき、
埋め込みを日本語の医学文で実測して比べ直す。

#### 層2 節・記事（既存の検索索引）

- 既存のサブスク索引に `filters: 'recordType:section'` で問い合わせ、上位3件。新しい索引は作らない。
- 節レコードは `src/lib/subscription-sections.ts` が作っており、`objectID` は `<親ID>#sec{n}`。
  主張の `section_key` と同じ規則なので、同じ節を指せる。
- 層1で既に出した節は層2から落とす（同じ場所を二度出さない）。
- 表示は 記事の題名 → 節見出し →「この節を読む」。

#### 層3 板の近い疑問

- `/api/cq/board` が返す5件を、層1と同じ覆い率で並べ替え、0.15 以上の上位2件。
  **0.15 は実測していない出発点**（層1の 0.25 より緩めに置いた値）。母数が5件しかなく、
  誤って出しても「近い疑問」として読まれるため、層1より緩くてよいという判断。
  層1と同じく定数として1か所に置き、`ask_shelf_queries` の記録を見て引き直す。
- 「私も気になる」は既存の投票 API をそのまま使う。上限（1日60回）も変えない。

#### 無料と有料（継ぎ目9）

- 主張の本文は有料。無料の利用者に返してよいのは、題名・節名・件数と「棚に無い」の1行まで。
- オーナー専用の期間は判定が要らないが、**返すデータを組み立てる段階で最初から通す**。
  後から足すと本文が漏れる。

#### 計測（更新案H）

`ask_shelf_queries` を1つ作る。列は 問い／層ごとの件数／最高覆い率／依頼に進んだか／作成時刻／利用者。
ここから「段0を見せた後に送らずに済んだ割合」を /admin に出す。

### 2. 利用者に見える状態は4つ（裁定3・更新案C）

判定は既存の `cq-mine.ts` の `stageOf` をそのまま使う。4段（received / onBoard / answered / closed）を既に返している。
足りないのは表示と理由だけ。

| 受付DB | stage | 見える文言 |
|---|---|---|
| 対応状態が空・ボード公開OFF | received | 受け付けました |
| 対応状態が空・ボード公開ON | onBoard | 検討中（板に出ています） |
| 対応済み | answered | 公開されました（飛び先つき） |
| 対応不要 | closed | 今回は記事化しません（＋理由） |

`src/lib/cq-dispatch.ts` の `dispatchLabel` に closed の分岐を足す。

**理由の置き場所は受付DBの新しい select 列「見送りの理由」。** 選択肢は5つ。

1. MediNode の対象外
2. 個別の症例の判断による
3. 既存の記事で答えられる
4. 根拠を確認できない
5. いまの制作範囲では扱えない

3つ目だけは「対応不要」ではなく **「対応済み」＋「正本主張ID（既存の主張）」と組ませる**。
利用者は答えが手に入るので、「記事化しません」ではなく「公開されています、ここです」が正しいため。
残る4つが「対応不要」と組んで「今回は記事化しません」になる。

これにより **受付DBに足す列は4つ**（継ぎ目4を3つから4つへ改める）。
段0結果（select: 該当あり／該当なし／未実行）／段0主張ID（rich_text）／正本主張ID（rich_text）／見送りの理由（select）。
既存の列は変えない。列が無い受付DBでも既存動線が壊れないこと（`buildIntakeProperties` は無い列を積まない）。

### 3. 正本主張IDの書き手は管理画面

/admin に「聞ける棚」パネルを1つ置く。

- 未対応の依頼の一覧。**段0結果＝該当なし で絞ったものが「空白候補ビュー」**（独立した保管場所は作らない）
- 各行で、ボード公開の切替／対応状態／見送りの理由／正本の主張の選択
- 主張の選択は語で検索して選ぶ。**24文字の鍵を手で写させない**（写し間違いは誰にも気づかれず、通知が飛ばないだけになる）
- 書き込み先は Notion の受付DB。Supabase に別の真実を作らない

**制作工程との受け渡し（`medinode-cq-note` の中身は変えない）**

1. 入口: /admin の空白候補から疑問文と背景をコピーしてスキルに渡す
2. 出口: 記事を公開 → サブスク同期で `recall_claims` に主張が入る → /admin で正本の主張を選ぶ
   → 「対応状態＝対応済み」と「正本主張ID」が Notion に書かれる
3. 通知 cron が次の実行で拾う

### 4. 回答通知（裁定4・更新案D/E、継ぎ目5の書き換え）

**飛び先は具体的な順に決める。** 純関数 `answerLandingUrl` に切り出す。

1. 正本主張ID があり、その主張が `recall_claims` にある → 着地画面 `/cq/answered/[id]`（節まで分かる）
2. 主張は分からないが記事は分かる → 着地画面から記事の先頭へ
3. 何も無い → アプリの入口（従来の振る舞い）

**「主張は無いが節は分かる」という段は置かない。** 節が分かるのは主張が `recall_claims` に
見つかったときだけなので、到達できない分岐になる（使われない分岐を残さない）。

URL は着地画面1つにまとめる。アプリには「記事の特定の節を URL で開く」経路が無く
（リーダーは `objectID` でアプリ内から開く。`src/lib/vine-open.ts`）、ここで URL の形を
新しく作ると開き方が二重の規約になるため。「主張＞節＞記事」の順位は、
着地画面が何を見せるかとして表す。

**着地画面 `/cq/answered/[id]`**（本人だけが開ける）に4つを並べる。
自分が送った疑問／回答＝正本の主張（本文と確信度）／根拠＝出典／「残す」と「この節を読む」。

**プッシュ**は cron の中で `sendToUsers(admin, [userId], 'resolved_cq', { title, body, url })` を1回。
種別 `resolved_cq`・設定トグル・`sw.js` のクリック先（payload の `url`）はすべて既にある。呼ぶ側だけを足す。
重複防止はメールと同じ `user_metadata.cq_answer_notified` を使い、1件につき1回。

**継ぎ目5の残り（2026-09-05 提案006の裁定1で書き換え）**。正本化の合図は「対応済み」かつ「正本主張ID が空でない」。
**cron は依頼者の `recall_progress` に書かない。** 「残した」になるのは、依頼者が着地画面の「残す」を押したときだけで、
そのときは既存の `/api/recall/keep` が通常どおり「間隔1日・期限翌日」で始める。
理由: 本人が押していない主張を出題母集団に入れない（継ぎ目10「一括操作を置かない」と同じ根拠）。
これにより「`due_at` を null にして初回閲覧から始める」という表現は不要になった
（`due_at` は `not null` で、離れかけの判定 `remainingOf()` は `due_at` を見ずに `last_reviewed_at` から計算するため、
null 方式はスキーマと計算の両方に合わなかった）。
フラグが閉じている依頼者にも着地画面は開けるが、「残す」は `recall` の内側でだけ描く。メール文面に Recall の名前を出さない。

### 8. 提案006「Nodeの情報構造」の裁定（2026-09-05）

比較の正は Notion「提案006 比較｜Nodeの情報構造（Claim＋利用者状態）（2026-09-05）」。
結論は「Node＝主張＋利用者状態」は現行の実装そのもので、新しい表は要らない。設計書に足すのは次の3つ。

**用語と実体の対応表**

| 語 | 意味 | 実体 |
|---|---|---|
| 主張 | 全利用者に共通する検証済みの1行 | `recall_claims` 1行。同期だけが書く |
| Node | その主張と自分の状態を合わせた、画面上の点（読む画面の行末の丸・Recall の点） | 描画時に `stateOf()` で合成。保存しない |
| 残した／読んだ／確かめた | 利用者ごとの状態 | `recall_progress`／`recall_section_reads`／`recall_review_log`。本人だけが書く |
| 定着 | 間隔90日以上の表示上の呼び名 | 計算値。列ではない |

UI 文言は「主張」のまま。コードの改名はしない（裁定6）。

**情報ごとの管理主体**

| 情報 | 管理主体 |
|---|---|
| 記事・節・主張の本文、確信度マーク、参考文献 | 作者（Notion） |
| 主張ID、節キー、`recall_claims` の行 | サブスク同期（`_core.ts`）だけ |
| 読んだ | 利用者の明示操作（節末ボタン） |
| 残した | **利用者の明示操作だけ**（読む画面の Node・Recall のカード・段0・着地画面の「残す」。すべて `/api/recall/keep`）。cron は書かない |
| 確かめた・間隔・期限 | アプリ（`srs.ts`）。利用者は「覚えた／まだ」を選ぶだけ |
| 依頼の原文・投稿時点の職種・経験年数・診療科 | 利用者の投稿（受付DBと `cq_submissions` に複製。後から変えない） |
| 対応状態・ボード公開・見送りの理由・正本主張ID | 作者（/admin から。Notion 手入力はしない） |
| 明るさ・離れかけ・次の期限・依頼の4状態 | アプリの計算 |

**裁定**

1. 正本化で cron が「残した」を書かない（上記4に反映）
2. `due_at` null の表現は不要になった
3. 「正本主張ID」は **/admin では1件だけ選ぶ**。読む側（`readIntakeColumns`）だけ配列を返す形にしておき、
   通知と着地画面は先頭の1件を使う。再検討ライン: 1つの依頼に2節以上で答えた実例が1件出たとき
