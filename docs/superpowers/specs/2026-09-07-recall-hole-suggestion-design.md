# Recall 想起カードに穴を付ける（AI に候補を出させ、オーナーが承認する）

日付: 2026-09-07
対象: `recall_claims` のうち、数値の穴が検出できなかった主張
関連: `2026-09-02-recall-engine-design.md`（伏せ字の規則・想起カード）、`2026-09-03-cycle-skeleton-design.md` 矛盾8、`2026-09-06-ask-shelf-stage1-design.md`（AI 呼び出しの型）

## 1. なぜ要るか

確かめるで出るカードの表に、思い出す対象が出ていない。

伏せ字カードになるのは `cloze_status='approved'` の主張だけで（`RecallCard.tsx`）、承認されていない主張は
**想起カード（全文伏せ）**として「この節の主張を思い出す」の1行だけを出す。これは
`2026-09-02-recall-engine-design.md` §165 のとおりの動作で、不具合ではない。

問題は2つある。

1. **承認が0件**。本番の `recall_claims` 725件は全部 `pending` で、伏せ字カードは1枚も存在しない（2026-09-07 実測）
2. **347件には穴の候補すら無い**。自動検出（`holes.ts`）は臨床の数値（閾値・範囲・用量）だけを穴にする規則で、
   数値を持たない主張には何も付かない

1 は承認を押せば解ける。2 は「どの語を伏せるか」を人が決めるしかなく、そこを AI の候補で埋める。

想起カードに冒頭の一句を手がかりとして出す案（矛盾8 の申し送り）は 2026-09-07 に実装して**破棄した**。
見分けはつくが答え合わせができず、記憶の練習にならない（オーナー判断）。穴埋めを本筋にする。

## 2. 実測（2026-09-07・本番データ）

### 主張の内訳（725件）

| | 件数 |
|---|---|
| 数値の穴が検出済み（承認待ち） | 378 |
| 穴なし・数字を含まない | 213 |
| 穴なし・数字はあるが研究統計として除外された | 134 |

`cloze_status` は 725件すべて `pending`（approved 0・rejected 0）。

### モデルの比較

穴なしの主張20件（等間隔抽出）に同じプロンプトを当てた。各1回。

| | Opus 5 | Sonnet 5 |
|---|---|---|
| 穴を作れた | **14/20（70%）** | 7/20（35%） |
| こちら側の検証に落ちた | 0件 | 0件 |
| 347件に伸ばした費用 | $3.11 | $0.94 |

向く／向かないの一致は 13/20。両方が穴を作った7件のうち範囲まで一致したのは3件で、
**食い違った4件はいずれも Opus の方が良い穴**だった（「8歳未満」対「歯牙の着色・エナメル質形成不全、一過性の骨発育不全」、
「Pplat − PEEP」対「ΔP 1-SD≈7 cmH₂Oの上昇で死亡リスク上昇」など。Sonnet は長い列挙をまるごと伏せる方向に外す）。

別に測った5件では Haiku 4.5 も当てた。5件中4件で無理に穴を作り、うち2件は列挙をまるごと伏せた。**採らない**。

**決定: `claude-opus-5`。** 費用差 $2.2 は一度きりの作業として小さく、覆う範囲（70% 対 35%）と穴の質の両方で上回る。

## 3. 候補の持ち方

**新しい列を作る。既存の `holes` には書かない。**

理由は2つ。`sync-claims.ts` は未判断（`pending`）の主張の `holes` を毎晩の同期で検出結果に上書きするので、
候補を `holes` に書くと翌朝消える。もう1つは、決まった穴と未承認の候補が同じ列に混ざると区別できなくなること。

migration `0033_recall_hole_suggestion.sql` で `recall_claims` に3列を足す。

| 列 | 型 | 中身 |
|---|---|---|
| `hole_suggestion` | jsonb | `[start, end]` 1件、または null |
| `hole_suggested_at` | timestamptz | AI を当てた日時。null なら未処理 |
| `hole_suggestion_note` | text | 「向かない」の理由、または失敗の記録 |

状態はこの3列だけで決まる。

- **未処理** … `hole_suggested_at IS NULL`
- **候補あり** … `hole_suggestion IS NOT NULL`
- **向かない／失敗** … `hole_suggested_at IS NOT NULL AND hole_suggestion IS NULL`

承認すると `holes` に移して `cloze_status='approved'` にし、`hole_suggestion` を消す。
見送ると `hole_suggestion` だけ消して `hole_suggested_at` は残す。**残すことで、次に走らせても再提案しない。**

**`sync-claims.ts` の upsert はこの3列を書かない。** `holes` と同じ理由で、毎晩の上書きが承認前後の判断を
消さないようにする（既存行の値をそのまま書き戻す。キーを外すと supabase-js の upsert が NULL で潰すため)。
新しい主張への候補付けは同期の**後段**で別に行う（§4）。upsert と同じ文で書かないことで、
「同期は既存の判断を触らない」という規則を1つに保つ。

## 4. 候補を作る流れ

### まとめて（`/admin` のボタン）

対象は `active = true AND holes = '[]'::jsonb AND cloze_status = 'pending' AND hole_suggested_at IS NULL`。

1回のリクエストで**20件まで**処理する。347件は1回のリクエストでは終わらない（1件2〜5秒）。
画面が「残り0件」になるまで繰り返し呼び、そのつど進み具合を出す。
途中で失敗しても処理済みの分は列に残るので、押し直せば続きから再開する。

### 自動（毎晩の同期）

同期の最後に、新しく入って穴が付かなかった主張を**最大20件**だけ処理する。溢れた分は翌晩に回す。
記事1本で増えるのは数十件（実績: 2026-09-02 に687件、2026-09-05 に38件）なので数日で追いつく。

### 呼び出しの作り

段1（`src/lib/ask-shelf/stage1-*.ts`）と同じ4分割にする。

| ファイル | 役割 |
|---|---|
| `src/lib/recall/hole-suggest-prompt.ts` | プロンプトと出力スキーマ。純関数だけ |
| `src/lib/recall/hole-suggest-verify.ts` | 返ってきた文字列の検証。純関数だけ |
| `src/lib/recall/hole-suggest-call.ts` | SDK に触るのはここだけ |
| `src/app/api/admin/recall/hole-suggest/route.ts` | POST。1回20件 |

モデルは `claude-opus-5` を既定にし、`RECALL_HOLE_MODEL` で切り替えられるようにする。
`ANTHROPIC_API_KEY` は段1で入れたものをそのまま使う（新しい環境変数は要らない）。

出力スキーマ（構造化出力・`zodOutputFormat`）。

```
{ suitable: boolean, span: string, reason: string }
```

**AI に文字位置は返させない。** 文字数を数えさせると必ずずれる。返させるのは伏せる範囲の文字列そのもので、
位置はこちらで求める。

## 5. 検証（AI を信じない部分）

`verifyHoleSpan(body, span)` が4つを確かめ、1つでも外れたら候補にしない。

1. `span` が本文に**ちょうど1回**現れる（0回なら創作、2回以上ならどちらの位置か決まらない）
2. 2字以上40字以下
3. 本文の全体ではない（伏せると何も残らない）
4. 既存の穴と重ならない

落ちたら1回だけ再試行し、それでも通らなければ「候補なし」として `hole_suggestion_note` に記録する。

緩めない理由は、伏せ字を開いたときに**原文と違う文字が出る**こと。医学の主張が1文字でも書き換わるのは、
この機能で一番まずい壊れ方になる。段1の形式検証と同じ fail-closed の流儀（`stage1-verify.ts`・`verifyVerbatim`）。

## 6. 承認画面

既存の `/admin`「Recall のカード」（`RecallCardsPanel.tsx`）にタブを足す。新しい画面は作らない。

- **タブ「AIの候補」** … 候補のある主張の一覧。1件ごとに表（候補の穴を当てた見え方）・裏（本文）・出典を出す。
  表の描画は既存の `segmentBody` をそのまま通すので、**読者に実際に出る見え方と一致する**
- ボタンは「この穴で伏せ字にする」「見送る」の2つ。穴がずれているときは既存の範囲選択でその場で直せる
- **タブ「向かない」** … AI が外した主張を理由つきで見るだけ。ここから手で穴を付けることもできる
- ボタンの近くに「未処理 n件・候補 n件・向かない n件」と、まとめて作るボタン

承認・見送りの操作は既存の PATCH（`/api/admin/recall/cards`）を伸ばす。監査ログ（`logAdminAction`）は
既存の `review_recall_cloze` に加えて、候補を作った回を `suggest_recall_holes`（件数とモデルを detail に）で残す。

**費用は列に保存せず、画面にも出さない。** 一度きりの作業で、段1のように読者が繰り返し踏む経路ではない。
アプリの中に単価の表を持つと、モデルの価格が変わったときに黙って嘘になる。画面には件数（処理した数・候補・向かない）
だけを出し、実額は Anthropic のコンソールで見る。監査ログにはモデルIDと件数を残すので、どのモデルで何件やったかは後から追える。

## 7. テスト

- `verifyHoleSpan` の純関数テスト（本文に無い・2回現れる・長すぎ・短すぎ・本文全体・既存の穴と重なる）
- **実データ回帰**。2026-09-07 に測った20件の結果を `.preview/recall-hole-fixture.json` に落とし、
  検証が通ることを固定する。`.preview` の無い端末ではスキップする（段1の `ask-shelf-fixture.json` と同じ扱い）
- API ルートのテスト（管理者以外は403・1回20件の上限・監査ログが残る）
- `sync-claims` が新しい3列を触らないことのテスト

## 8. やらないこと

- 候補を複数出す（1件1つに絞る。3つ検分するより1つ選ぶ方が承認が速い。あとから手で足せる）
- 数値の穴がある378件に語の穴を足す（数値の穴で足りる）
- 「向かない」約104件の手当て（実物を見てから決める）
- 想起カードの表に手がかりを出す（2026-09-07 に実装して破棄。§1 のとおり）

## 9. 完了条件

オーナーが本番で候補をまとめて作り、`/admin` で承認し、確かめるで**穴あきのカードが出る**ことを確認した。

## 10. 再検討ライン

- 「向かない」が実測で **5割を超えた**とき。穴埋めだけでは想起カードが減らないので、想起カードの作りに戻る
- 承認した穴のうち、オーナーが手で直した割合が **3割を超えた**とき。プロンプトか検証の規則を見直す
