# 外の輪（棚を育てるサイクル）設計

日付: 2026-09-02
状態: オーナー承認済み（会話で段階確認）。実装計画は未着手
先行資料: 双輪サイクルの骨格（2026-09-01・設計セッション。正はNotionの🎬プロジェクト_DB「MediNode アプリ開発」配下）／
`docs/superpowers/specs/2026-08-31-source-acquisition-ledger-design.md`

## 背景・課題

MediNode の疑問まわりの入口は現在3つに割れている。検索（Algolia・ページ単位）、
CQ投げ込み（受付DBへ送る）、記事の節末の「気になる」。
このうち投げ込みは、送っても答えが返るまで日数がかかる。AIに即答を求める習慣がある
利用者にとって「投げるだけ」は続かない。一方で検索はページに着地して終わり、
そのページが答えでなければ行き止まりになる。

共通しているのは「一方通行で、返ってこない」ことである。
本設計は、疑問が湧いてから正本の主張になるまでを1本の階段にまとめ、
どの段でも必ず何かが即座に返るようにする。

## 用語

- **粒**: 検証済みの主張1つ（原文＋出典を伴う）。ページではなく主張1行が単位
- **棚**: 粒の集合。公開済みのコーパスから作る
- **段0 / 段1 / 段2**: 階段の各段。下に降りるほど時間と費用がかかる

## 決定事項（サマリ）

1. **入口は1本の階段にする。** 疑問を書く → 段0（棚を引く）→ 段1（AIに組ませる）→
   段2（作者に検証を依頼）。CQ投げ込みは廃止せず、階段の最下段に降格する。
2. **段0は AI 生成をしない。** 返すのは検証済みの粒（主張＋原文＋出典）だけ。
3. **段0が該当なしのときも近い粒を弱い確度で出す。** ただし
   「この問いそのものの粒はまだ棚に無い」の1行を必ず添える。手ぶらで返さないことと、
   棚の空白を隠さないことを両立させる。
4. **段1は明示的なボタンで踏む。** 自動では降りない。答えには全体に「未検証」を出し、
   粒を引用した部分と AI が補った部分を区別する。
5. **段1の答えは蒸発させない。** MediNode 側に残し、Notion 接続済みの利用者は
   自分の Notion にも落ちる。Notion 接続は必須にしない（クラウドセーブ扱いを維持）。
6. **段2の依頼は「棚の空白候補」に自動で積む。** 段0が該当なしだった事実を添える。
   板（未解決CQボード）への掲載は作者の承認を残す。
7. **正本になったら依頼者に通知する。** 実装中の `cq-answer-notify`（メール・cron）を仕上げる。
8. **段0で引いた粒はその場で拾える。** 内の輪への入口をここに置く。
9. **依頼した問いが正本の粒になったとき、依頼者にはその粒が最初から拾われた状態で入る。**
10. **drnode.com での公開判断まで、この機能は一般の利用者に出さない。**
    既存の先行体験（`feature-access.ts`）に機能名を足し、オーナーだけが本番で使える状態にする。

## 階段の契約

| 段 | 入力 | 返すもの | AI生成 | 費用 | 応答時間 |
|---|---|---|---|---|---|
| 段0 | 自然文の疑問 | 検証済みの粒を数件（主張・原文・出典） | なし | 実質ゼロ | 即時 |
| 段1 | 疑問＋段0の粒 | AIが組んだ答え＋引用チップ | あり | 1問あたり数十円規模のAPI費 | 数秒〜数十秒 |
| 段2 | 段1でも残った問い | 正本の粒 | 制作工程による | 作者の工数 | 後日（通知） |

### 段0（棚を引く）

- 対象は公開済みコーパスから作った**粒のインデックス**。
  現行の Algolia インデックスはページ単位なので、粒のインデックスは新設する。
- 自然文の疑問を受けるため、キーワード一致だけでは不足する。検索方式は実装計画で決める
  （埋め込みの種類・更新頻度を含む）。
- 表示単位は粒。粒ごとに主張・原文・出典・確信度を出す。
- 各粒に「拾う」を置く。拾う先の設計は内の輪の設計に属する（本設計では接点だけを定める）。

### 段1（AIに組ませる）

- 段0の結果画面からボタンで踏む。踏まないかぎり課金対象の処理は走らない。
- プロンプトには段0で引いた粒を渡す。棚にある内容は棚の言葉で答えさせる。
- 表示規約:
  - 回答全体に「未検証」を出す
  - 粒に由来する記述は引用チップを付け、原文と出典へ辿れる
  - 粒に無い内容を AI が補った部分は、由来なしとして区別する
- 保存: MediNode 側に質問と回答を残す。Notion 接続済みなら自分の Notion にも書く。
- v1 はオーナー専用で実測する。開放範囲と費用方式は実測後に決める。

### 段2（作者に検証を依頼）

- 依頼は既存の受付DBに入る（`cq-submit` の経路を変えない）。
- 依頼レコードには段0の結果（該当なしだったか、引かれた粒は何か）を添える。
  作者はこれを見て、棚の空白かどうかを判断できる。
- 「棚の空白候補」は独立した保管場所を新設せず、受付DBの1ビューとして持つ
  （依頼レコードに段0の結果を書き、それで絞る）。運用と集計を二重化しないため。
- 板への掲載は作者の承認を経る。板の同時掲載上限と、票0を出さない方針は変えない。
- 検証が済んで正本の粒になったら、依頼者にメールで通知する。

## 公開の門（drnode.com の公開判断まで隠す）

本設計の機能は大型アップデートの一部であり、drnode.com で MediNode を出す判断をするまでは
一般の利用者に表示しない。オーナーだけが本番環境で使える状態にする。

- **新しい仕組みは作らない。** 既存の先行体験（`src/lib/feature-access.ts` ＋
  `user_settings.early_access_features`）に機能名を1つ足すだけにする。
  機能名は `ask_shelf`（外の輪の階段）。内の輪は別の機能名を持つ。
- **専用のメールリストのみを持ち、フォールバックは付けない。**
  他の先行体験を誰かに開いた瞬間に、この機能まで見えてしまうのを防ぐ
  （`tower` を `multi_department` から分離した前例に合わせる）。
- **判定の正はサーバー。UI を隠すだけにしない。** 段0・段1・依頼の各 API は、
  処理を始める前に `hasFeature('ask_shelf', …)` を通す。とくに段1は API 費用が発生するため、
  閉じているときは課金対象の処理へ入らせない。
- **閉じているあいだ、既存の動線は今までどおり動く。** 階段は既存の検索・CQ投げ込みを
  置き換える形では実装せず、フラグの内側にだけ現れる。フラグを閉じ直すだけで元に戻る。
- **受付DBに足す列（段0の結果）は、フラグの外側でも壊れないようにする。**
  列が空のままでも、既存の板・投票・通知は従来どおり動く。
- **公開判断のときにやることは、GA env（`ASK_SHELF_GA=true`）を立てるだけにする。**
  コードの書き換えを公開作業に含めない。

## 既存部品の扱い

| 部品 | 扱い |
|---|---|
| `src/lib/cq-submit.ts` | 残す。位置づけを階段の最下段に降格 |
| `src/lib/cq-board.ts` ＋ 投票API | 残す。供給元を作者の手入力から「棚の空白候補」に変える |
| `src/lib/cq-mine.ts` / `cq-dispatch.ts` | 残す。階段の履歴表示に流用 |
| `src/lib/cq-answer-notify.ts` ＋ cron | 仕上げる。外の輪を閉じる最後の1本 |
| `src/lib/algolia.ts`（ページ単位検索） | 残す。段0の粒インデックスは別に新設 |

## 本設計で決めないこと

- 段1の開放範囲と費用方式（オーナー専用での実測後に判断する）
- 粒インデックスの作り方（検索方式・更新頻度・粒の抽出手順）
- 段1の答えが後日正本の粒に置き換わったときの見せ方
- 内の輪（拾う・回す・体得）の設計。本設計は接点のみを定める

## 検証の考え方

- 段0は AI を含まないので、正しさは粒の正しさに帰着する。粒の正しさは既存の検証工程
  （出典台帳・取得ラダー・層2/層3）で担保する。本設計で新しい検証層は作らない。
- 段1は未検証である。未検証であることを表示で担保し、正本と混ぜない。
- 実装時は、段0が該当なしのときに「棚に無い」の1行が必ず出ることを回帰テストで固定する。
