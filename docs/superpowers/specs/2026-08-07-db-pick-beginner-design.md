# DB選択を初心者向けにする 設計（2026-08-07）

実機フィードバック（オーナー・2026-08-07）：かんたん接続の仕上げシートについて「文字が多すぎる」「かんたん接続って何、他と何が違うのという混乱を招きかねない」「`Medical DB` `Reference DB` みたいなのが突然出てくると、自分のNotionの何を選んでいいのか分からない人もいる」「マニュアルも」「セットアップ画面にどんなDBを選ぶといいのかが書いてあるといい」。

方針は1つ、**初心者が画面の言葉だけで判断できるようにする**。

## 1. 役割の呼び方を、アプリで見える場所に揃える

`Medical DB` / `Reference DB` / `Manual DB` は、アプリの画面のどこにも出てこない語である。3つとも「読み取ると、どのタブに出るか」で言い換える。

| いまの表示 | 変更後 | 補足（画面に出す） |
|---|---|---|
| Medical DB（必須） | **知識**（必須） | 検索と新着に出ます |
| Reference DB（文献・任意） | **文献**（任意） | 文献タブに出ます |
| （選べない） | **マニュアル**（任意） | マニュアルタブに出ます |

`ROLE_LABEL`（`OAuthFinish.tsx:43`）は conflict / unreadable の文中で使われており、そちらも同じ語に揃える（「知識本体のデータベース」→「知識のデータベース」）。

## 2. 「どんなDBを選ぶといいのか」を1行で置く

かんたん接続の仕上げシートと、手動セットアップのNotionステップの両方に、同じ1文を置く。

> 症例メモや勉強ノートなど、**検索したい記事が1行1件で並んでいるデータベース**を選びます。

テンプレートから作った人にはそのまま当たり、自分のDBを使う人には判断の手がかりになる。

## 3. 当たっているときは確認、外れているときだけ選ばせる

いまのプリフィルは**保存済みの設定を持っている人にしか効かない**（`OAuthFinish.tsx:135-143`）。かんたん接続で初めて入った人は全欄が空で、`Medical DB（必須）` と言われて「選んでください」に当たる。ここが今回の混乱の中心。

**名前からの推し当て**を足す。純関数 `guessDbRoles()` に切り出し、次の順で決める。

1. 保存済みの設定と一致するDB（現行の正規化ID突き合わせ。ここは変えない）
2. 空いている役割を、DB名で推し当てる
   - 文献 … 名前に `文献` / `参考` / `reference`（大文字小文字を問わない）
   - マニュアル … 名前に `マニュアル` / `manual` / `お知らせ` / `手順`
   - 知識 … 名前に `medical` / `知識` / `ナレッジ` / `knowledge` / `症例`
3. それでも知識が空で、まだどの役割にも就いていないDBがちょうど1件なら、それを知識にする（現行の「候補が1件だけなら自動選択」を一般化したもの）

同じDBが2つの役割に就くことはない（先に決まった役割が優先）。

推し当ては**既定値を置くだけ**で、決定ではない。名前は画面に出るので、外れていれば気づける。

**画面の出し方**

- 決まった役割は選択欄ではなく確認行にする — 「`My MEDICAL _DB` → 検索と新着に出ます」
- 変えたい人のために、確認行の下に「別のデータベースを選ぶ」を小さく置く（押すと選択欄に変わる）
- 決まらなかった必須（知識）は、最初から選択欄を出す
- 任意の2つ（文献・マニュアル）は、決まっていなければ**畳んでおく**。「文献やマニュアルも読み取る」で開く

これで、テンプレート利用者が見るのは「確認行3つとボタン1つ」になる。分量の指摘への回答でもある。

## 4. マニュアルを選べるようにする（穴を塞ぐ）

いまの仕上げシートはマニュアルを扱わない。`save()` は `...s` で既存値を残すだけなので、**かんたん接続だけで設定した人はマニュアルタブに永久にたどり着けない**。文言ではなく機能の穴なので、ここで塞ぐ。

- 選択欄・確認行をマニュアルにも用意する
- `save()` に `notionManualDbId: manualId` を足す

**追加の読み取り確認はしない。** 候補は `list-databases` が返した一覧、すなわち今回のトークンで実際に見えたDBだけである。一覧から選ばれたDBは読めることが確定しているため、`check-props` に項目を増やす必要はない（`check-props` は列マッピングの推定に使うもので、対象は知識のDBだけでよい）。

## 5. 触らない範囲

- conflict / unreadable / claimCheckFailed の**判定ロジック**（§20c）。文中の役割名だけ1と揃える
- 手動接続の入力欄（Token・DBのURL）。ここは既存ユーザーの操作記憶があるため、今回は説明文の1行追加だけ
- 「かんたん接続とは何か・手動接続と何が違うのか」の説明。これは入口側（設定・セットアップ）の話で、この画面の外。別途扱う

## テスト

- `guessDbRoles()` の単体テスト：保存済み優先／名前一致（3種）／重複割り当てなし／残り1件の知識自動選択／何も当たらないとき空
- 既存テストが全て通ること（この画面にDOMテストは無い。表示は実機で確認する）
