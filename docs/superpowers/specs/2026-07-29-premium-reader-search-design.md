# プレミアム読書体験 第3波 — リーダー内検索＋横断本文検索＋つづけて読む枠 設計

- 日付: 2026-07-29
- ステータス: 設計承認済（オーナー 2026-07-29）
- 前提: リーダー v2（結論バー/目次・確信度フィルタ・読了/ブックマーク）は main マージ済。
  本 spec は v2 spec（`2026-07-23-subscription-reader-v2-design.md`）で fast-follow と
  先送りされた「ページ内検索」を本命に、プレミアム機能のブラッシュアップとして
  横断本文検索と「つづけて読む」枠（`2026-07-29-reader-related-content-footer-design.md`）
  を1本の流れに束ねる。

## 背景・目的

プレミアムナレッジは1記事が長い（6セクション＋Evidence、数千字）。v2 の目次・確信度
フィルタで「拾い読み」はできるようになったが、**「あの数値どこだっけ」（記事内）と
「あの話どの記事だっけ」（記事横断）に答える検索が無い**。また📖参考文献節の廃止
（2026-07-29）で、読了後の導線の受け皿（つづけて読む枠）が未実装のまま残っている。

3機能を「**探す → 読む → 次へ進む**」の1本の流れとして実装する：

1. **機能① リーダー内検索** — 開いている記事の中をキーワード検索（クライアント完結）
2. **機能② 横断本文検索** — 全プレミアムナレッジの本文を節単位で串刺し検索（プレミアム限定）
3. **機能③ つづけて読む枠** — 読了位置に根拠文献＋関連ナレッジ（既存 spec 準拠）

ナレッジ相互リンク（低Na⇄低K等・v2 の先送り項目）は機能③の「関連ナレッジ」欄が
受け皿。手動リンク機構は作らない（オーナー決定 2026-07-29: 手動キュレーションは腐る）。

## アーキテクチャ前提（調査済みの事実）

- リーダー本文: `/api/subscription/page` が Notion から取得し `mapBlocksToReaderDoc` で
  ReaderDoc 化、Vercel Data Cache 1h＋sync 時 revalidateTag。**クライアントは本文全体を
  ReaderDoc として保持している** → 機能①はサーバー変更ゼロで成立。
- 検索基盤: Algolia。サブスク用インデックスはプレミアム会員だけに発行される
  **短命 Secured Key（validUntil＋restrictIndices 焼き込み）でクライアント直検索**
  （`src/lib/algolia-secured.ts`）。→ 本文を載せても非会員からは物理的に触れない。
  ペイウォールは既存機構のままで成立する。
- sync: `/api/subscription/sync/_core.ts` は既に**全ページの本文トップレベルブロックを
  取得している**（充実度統計 `fetchContentStats` 用）→ 本文テキスト抽出の追加コストは
  ほぼゼロ。現在インデックスに本文は入っていない（title/genre/要約/キーワード/headings のみ）。
- 現規模: サブスクナレッジ約40ページ。

## 実装順

1. **機能①** リーダー内検索（サーバー変更なし・単独デプロイ可・即効性最大）
2. **sync 拡張** 機能②の節レコード＋機能③の参考文献リレーション同期を一括改修
3. **機能③** つづけて読む枠 UI
4. **機能②** 検索結果カードの本文ヒット表示＋リーダー deep-link 連携

## 機能① リーダー内検索

### UI

- リーダーのナビバー（ReaderNavBar）に検索アイコンを追加。既存の結論バー・CQ捕捉FABと
  干渉しない配置。
- タップでシート上部に検索バーが出る（sticky）。閉じるとハイライト・状態を全解除。
- ヒット件数「3/12」＋前/次ボタン。前/次で該当ブロックへスクロール（v2 目次ジャンプの
  スクロール機構を流用）。現在位置のヒットは強調色、他は淡いハイライト。
- 0件時は「見つかりません」を静かに表示（宣伝調・AI主役の文言は使わない）。

### 挙動

- クライアント側で ReaderDoc の全ブロックテキストを線形走査。数百ブロック規模なので
  性能問題なし。
- 正規化: 全角/半角・大文字小文字・カタカナ/ひらがなは正規化してマッチ
  （純関数 `normalizeForSearch`）。
- IME 対応: composition 中は検索を発火しない（compositionend 後に発火）。
- ハイライト: ブロックのテキストノードに `<mark>` 相当の span を注入する純関数
  `highlightMatches(block, query)`。React レンダリング側で安全に適用（dangerouslySetInnerHTML
  は使わない）。
- 確信度フィルタとは独立に動作（フィルタで淡色化された行もヒット対象・ジャンプ可）。
- 外部連携口: リーダーを開く際に `initialQuery` を受け取れるようにする（機能②から
  検索語を引き継いで自動ハイライト・該当節スクロール）。

## 機能② 横断本文検索（プレミアム限定）

### 方式（承認済み: 案A＝セクション単位の子レコード）

- sync 拡張: 各ページの本文ブロックを `## N.` 見出しで節に分割し、節ごとに子レコードを
  登録する。
  - objectID: `subscription_<pageId>#sec<N>`
  - フィールド: `parentId`（`subscription_<pageId>`）, `recordType: 'section'`,
    `sectionNo`, `sectionTitle`, `sectionText`, ＋表示用に親の `title`/`genre`/
    `detailGenre` 等の最低限。
  - `## 1.` より前（⚡結論・🧑‍⚕️署名・査読スタンプ・大前提）は `sec0` として1レコード。
  - 1節が 10KB を超える場合は文単位で分割して複数レコード化（`#sec<N>-2` 等）。
- 純関数 `splitIntoSections(blocks)` に切り出してユニットテスト。
- Algolia 設定:
  - `attributeForDistinct: 'parentId'`＋`distinct: true` → 検索結果はページ単位に集約され、
    最も関連の高い節が代表ヒットになる。
  - **既存の親レコードにも `parentId`（＝自身の objectID）を付与する**。これが無いと
    親と節が distinct で同一グループにならず、同じページが検索結果に二重に出る。
  - `searchableAttributes` に `sectionText`/`sectionTitle` を追加（title より低優先）。
  - `attributesToSnippet: ['sectionText:30']`。**`sectionText` は
    `attributesToRetrieve: ['*', '-sectionText']`（インデックス既定）で応答から除外し、
    スニペット（`_snippetResult`・ハイライト付き）のみ返す**。
    （注: `unretrievableAttributes` はスニペットまで消えるため使わない。会員は
    本文APIで全文を取得できるため、クエリ時上書きが残ることは新たな露出面ではない。）
- 既存の親レコード（ページ単位）は現状のまま維持。節レコードは追加分なので、
  節レコード生成に失敗しても従来検索は壊れない。
- 規模感: 40ページ×8節前後＝約320レコード。Algolia の枠に問題なし。

### 検索 UI

- 既存のプレミアム検索結果カード（ResultCard）に「本文ヒット」表示を追加:
  §番号＋節タイトル＋ハイライトスニペット。
- 本文ヒットをタップ → リーダーを該当節までスクロールした状態で開き、機能①に検索語を
  渡して自動ハイライト（`initialQuery`＋`initialSectionNo`）。
- 非会員: サブスク用インデックスの Secured Key 自体が渡らないため、本文ヒットは
  存在ごと見えない（現行と同じゲート。追加実装なし）。

## 機能③ つづけて読む枠

`2026-07-29-reader-related-content-footer-design.md` の仕様に準拠（本 spec では変更しない）:

- 位置: リーダー本文末尾（免責の下）。
- **根拠文献**: `参考文献` リレーション実登録分。収録レベルバッジ（📄/🔖）付き。
  0件なら見出しごと非表示。
- **関連ナレッジ**: 自動算出（同一詳細ジャンル > 同一ジャンル、キーワード重複で
  スコアリング、上位3件程度、自分自身除外）。タップでリーダー内遷移。
- 手動キュレーション用のプロパティ・本文節は作らない。トーンは静か
  （「つづけて読む」等。AI主役の宣伝的文言NG）。

本 spec での接続点:

- `参考文献` リレーション（ページID配列）の同期は、機能②の節レコード同期と
  **同じ sync 改修に相乗り**させて一度で済ませる。
- 関連ナレッジのスコアリングは純関数化してユニットテスト。

## 品質・エッジケース

- 純関数（`normalizeForSearch` / `highlightMatches` / `splitIntoSections` /
  関連スコアリング）はユニットテストを書く（TDD）。
- sync: 節レコード生成・リレーション同期の失敗はページ全体の同期を止めない
  （現行 `fetchContentStats` と同じ「失敗しても続行」方針）。
- 機能①はダークモード両対応（生CSSのダークは `.dark` 基準。`@media` 禁止）。
- SW キャッシュ: デプロイ時に CACHE_VERSION を上げる（現行運用踏襲）。

## やらないこと

- 手動のナレッジ相互リンク機構（腐るため。関連ナレッジ自動算出が受け皿）。
- 非会員向けの本文ヒット・ティーザー表示（今回はスコープ外。将来の転換施策として検討可）。
- 出典その場展開・用量→計算ツール・「今日の1問」からリーダー直行（v2 先送り項目の
  残り。ロードマップDB管理のまま）。
- Supabase 全文検索など新しい検索基盤の導入（Algolia で足りる）。
