この文書は、設計書を読まなくてもセッションを開けるように、部品ごとに「着手条件・決めること・作るもの・守る継ぎ目・借りるパーツ・完了条件・最初の一言」だけを抜いたもの。
矛盾があれば設計書が勝つ。

## 進め方の約束（全セッション共通）

- 1部品＝1セッション。同じ main に2本を走らせない。worktree を切る（`superpowers:using-git-worktrees`）
- 設計が要る部品は `superpowers:brainstorming` → 設計書 → `superpowers:writing-plans` → 実装。要らない部品は `writing-plans` から
- 実装はサブエージェント方式（`superpowers:subagent-driven-development`）。実装 Sonnet 5・レビュー Opus 5
- テストは実データ（`.preview/` の主張コーパス、受付DBの実物、本番 cron の手動実行）
- push は毎回オーナーの承認。公開リポなので事業数値を書かない
- 完了条件は「オーナーが本番で実測した」。実装が終わっただけでは閉じない
- セッションの終わりに `/shime`。引き継ぎは `~/.claude/handoff/app.md`

## 部品1 読む画面の「残す」と「読んだ」

- **目的**: 内の輪の入口を読む画面に付ける
- **着手条件**: Recall でサブスク同期を1回押して `recall_claims` に主張が入り、残す→確かめる→覚えた の一周が本番で通っている
- **作るもの**: サブスクのアプリ内リーダー（`ReaderBody`・`ReaderSpread`）の主張行に「残す」の切替（長押しでも効く）。節末に「この節を読んだ」の明示ボタン。既存 API `/api/recall/keep`・`/api/recall/read` を呼ぶ。`hasFeature('recall')` が偽なら描かない
- **決め済み（変えない）**: 「残す」を置く行は `extract-claims.ts` の `splitClaim` が主張と判定する行だけ。`claimIdOf(ページID, 本文)` を共有関数で計算し `/api/recall/claims` の一覧と突き合わせ、無い行には置かない。節番号は `sec{n}`。スクロール自動判定なし。端末ローカルの読了水位（`ReaderMarksProvider`）と統合しない。一括操作なし
- **借りるパーツ**: 長押しで印（Matter）
- **完了条件**: オーナーが本番で記事を読み、主張行で「残す」→ 球に灯る → 節末「読んだ」→ 球に灰青で灯る、を確認
- **最初の一言**: 「実行リストの部品1を superpowers:writing-plans で計画し、superpowers:subagent-driven-development で実装してください。設計書の部品1の要点と継ぎ目1〜3・10を守ること。worktree を切り、push は承認を取ってから」

## R Recall への申し送り（Recall セッションで扱う）

- **明るさを「思い出せる確率」に**: R(t) = (1 + (19/9)·t/S)^(-1)、S は現在の間隔日数。段は固定のまま状態層の式だけ変える。離脱閾値も引き直す
- **「覚えた／まだ」を3択に**: 「もう一度／来週／しばらく先」（日数ラベル。Readwise Mastery の型）
- **伏せ字の数を記憶度で変える**: 暗いほど穴1つ、明るいほど上限3。**実装前に特許 JP7495135B2（Monoxer）の請求項を読む**
- **想起カードの手がかり**: 冒頭の一句（最初の読点まで）を表に出す
- **`due_at` が null の行**: 「残したが未開封」として候補から外し、球では「残した」の色で灯す（継ぎ目5の前提）
- **最初の一言**: 「Recall の設計書に、実行リスト（`docs/superpowers/plans/2026-09-03-cycle-skeleton-sessions.md`）の R 節の5点を反映する計画を立ててください。特許の確認は請求項を読んだ結果を先に報告すること」

## 部品3 聞ける棚の段0＋段2（設計セッション → 実装）

- **目的**: 疑問が棚に当たり、無ければ依頼になり、正本になって戻る経路を作る
- **着手条件**: Recall セッションが同期側（主張の抽出・穴・承認）のコードを触り終えている
- **設計セッションで決めること**
  1. 段0の検索方式: 埋め込みの提供元（OpenAI 3-small／Gemini／Cohere embed-v4 を日本語の医学文で実測）＋日本語全文検索（PGroonga）の併用。列は `recall_claims` に足す。更新は同期の中
  2. 「棚に無い」の閾値（類似度と件数。Consensus の「材料が足りなければ出さない」の型）
  3. 「正本主張ID」の書き手（管理画面の操作か Notion 手入力か）
  4. 制作工程との受け渡し: CQ スキルが受付DBの依頼を入口として読む手順と、正本化で「対応済み」＋「正本主張ID」を書き戻す手順（スキルの中身は変えない）
  5. 依頼画面の期待値の文言（「平均○日・正本化率○%」の枠。実測後に数を入れる）と、「対応不要」の理由表示
  6. 依頼の種別に「訂正」（この主張は違う）を足す。受付DBの既存列で足りるか
  7. 依頼フォームの必須項目（背景・状況、何を調べたか。Antaa の質問テンプレの型）
  8. 空白候補ビュー（受付DBの1ビュー。段0結果＝該当なしで絞る）
  9. 音声入力を窓に置くか（転写→疑問文の形に整えるだけ。整形なしも選べる）
  10. 段0の結果に出す検証者名と検証日（データの有無を確認）
  11. 「棚に無ければ答えない」をヘルプに仕様として書く文言
- **作るもの**: 検索タブの窓の上に主張の段（あるときだけ開く・折りたたみ）、各主張に「残す」「この節を読む」「関連する主張3件」、自分が残した主張の最上位表示と印、「棚に無い」の1行、結果末尾の「作者に検証を依頼」、受付DBの列3つ（段0結果／段0主張ID／正本主張ID）、通知 cron の継ぎ目5対応（`due_at` null で「残した」を書く）、`ask_shelf` フラグ（`ASK_SHELF_EMAILS`・フォールバック無し）
- **守る継ぎ目**: 1・2・4・5・6・7・8・9
- **オーナー作業**: Supabase で pgvector（と PGroonga）を有効化、埋め込み API キーを `.env.local` と Vercel へ、`ASK_SHELF_EMAILS` にオーナーのメール、マイグレーション 0030 を流す
- **完了条件**: オーナーが本番で疑問を書き、段0が主張を返す／「棚に無い」を出す → 依頼 → 制作工程で正本化 → 同期 → メールが届き、球に「残した」で灯る（期限は初回閲覧から）
- **最初の一言**: 「実行リストの部品3を superpowers:brainstorming で設計してください。設計書の部品3の要点・継ぎ目・仕組み台帳・深掘りの 1・2・14・15・19・20 を入力にすること。設計が承認されたら writing-plans へ」

## 部品6 今日の1問の撤去＋週1の便り

- **目的**: 内の輪を外から引く便りを置き、今日の1問を消す
- **着手条件**: 部品1〜3をオーナーが一周した後
- **作るもの**: 撤去は Recall 設計書「今日の1問の撤去範囲」の表のとおり。週1の便り（Web Push と Resend。メールを止めてもアプリ内の棚に残る）。中身は「今週確かめる主張が n 件」＋傾向1行＋偶然の1行（利用者 ID と週のハッシュで決定的に選ぶ）。0 件なら送らない。曜日の設定（当直の曜日を避ける）
- **傾向の計算**: `recall_review_log`・`recall_progress`・`recall_section_reads`・`recall_claims` の SQL だけ。出してよいもの: 区画ごとの「まだ」率、残した主張の区画の偏り、読んだが残していない節、棚にあって触れていない区画、「まだ」が続く主張の一覧。出してはいけないもの: 点数・順位・赤・責める文言。「得点や順位は能力を認定しない」の断り
- **ここで判断**: クイズタブの端末記録（`quiz-srs.ts`）を Recall へ移すか捨てるか

## 部品7 記載フォーム＋昇格描画（設計セッション → 実装）

- **目的**: 利用者が MediNode に適した書き方を覚えなくても、Notion にもアプリにも綺麗に出る
- **着手条件**: 部品1の後。/admin の個人・部署リーダーの計測（ブロック分布・離脱タップ）を見てから
- **設計セッションで決めること**
  1. フォームの項目。必須は主張と出典だけ。分野は自動候補（本文を埋め込み、ラベル付きの主張 700 件で最近傍の多数決）
  2. 取り込み経路。最初の追加経路は共有シート。URL（OGP で題名・著者・日付を取り、AI は要約だけ）、スクショ（文字起こし）、音声（転写→整形、整形なしも選べる）
  3. AI 補助の線引き: 形を整えるだけ。補助で入った行は ❓ 既定＋AI 由来の記号。✅ にできるのは出典を伴う行だけ
  4. 規約ブロックの組み立て（Tally の「回答を本文の穴に差し込む」型）。`pages.create` に properties＋children
  5. v1 は新規作成のみ。画像の Notion 保存はファイルアップロード API の版を確認（未確認）
  6. 昇格描画の判定（規約に沿うページだけスプレッドと同じ見え方）と、既存の降格式リーダーとの切替
  7. 複製テンプレ（`notionDuplicatedTemplateId`）の更新。教育はしない
  8. CQ Catcher との線引き
  9. 費用（文字起こし・要約）
- **守る継ぎ目**: 12
- **完了条件**: オーナーが本番でフォームから1ページ作り、自分の Notion に規約どおりのブロックで入り、アプリで昇格描画される
- **最初の一言**: 「実行リストの部品7を superpowers:brainstorming で設計してください。設計書の部品7・継ぎ目12・仕組み台帳・深掘りの 1・3・5・6 を入力にし、2026-08-12 の判断（教育しない・要点モードは個人に出さない）との整合を最初に確認すること」
