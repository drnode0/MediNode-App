## 全体の制約

- **テストは DOM を持たない。** `vitest.config.ts` に `environment` の指定が無く、`@testing-library/*` も入っていない。
  したがって**判断のロジックはすべて純関数に出し、その純関数をテストする**。canvas の描画そのものはテストせず実機で見る。
  この計画で新しく足す純関数は、既存の `layout.ts` / `srs.ts` と同じく**描画を知らない**こと
- **決定1〜13 を実装で動かさない。** 迷いが出たら設計書に戻る。設計書に無いことは決めずに、この計画の「実装時に確認すること」へ足す
- **線画。** 面・塗り・影を使わない。光（`INK_HALO`）は動きと離れかけにだけ
- **画面に出す語は「深く残した／残した／離れかけ／読んだ／未着手」**（決定9）。「定着」は画面に出さない。
  内部名 `settled`・DB列・`SETTLED_MIN_DAYS` は据え置き
- **文言の禁止語彙を守る。**「振る」「拾う」「血肉」「落ちる」は UI 文言に使わない（外へ「離れる」）
- **記録の意味を変えない。** `recall_progress` / `recall_section_reads` / SRS の段は一切触らない。この計画は見せ方だけ
- **動きを減らす設定**（`useReducedMotion`）で、芯の動き・明滅・弧・カメラの飛びを止め、位置の変更は即時にする
- ダッシュ「——」を使わない

## Task 段6: リスト表示（**未決。オーナーの判断待ち**）

「絵ではなく文字で見たい」利用者のための、惑星と同じ内容のリスト。**まだ決まっていない。**
段5まで終えてから着手する想定なので、この判断で段1〜5は止まらない。

### Claude Code の推奨: 入れる。ただし主要ナビにしない

理由が3つある。

1. **canvas は支援技術に何も出さない。** 惑星も球も、読み上げには存在しない画面になる
2. **明るさから記憶の状態は読み取れない。** 不透明度は「状態 × 光の当たり × 奥行き × 保持力」の積で、
   保持力による差（約1.8倍）は奥行き（約8.3倍）や光（約3.8倍）より小さい。
   引きで全体の面積を眺める用途では問題にならないが、「どれが離れかけか」を目で確かめる手段が無い。
   **「次は◯日後」を数字で出す場所**が要る
3. 低性能端末の代替になる

一方で、リストを主要ナビゲーションに据えると惑星が装飾に落ちる。**既定は惑星、リストは切り替え**にする。

### 構成案

- 席 → 記事 → 主張 の三段。`RecallProvider` が `claims` / `progress` / `reads` を素の配列で持っているので、**データ層の追加はゼロ**
- 各主張に**状態名**（深く残した／残した／離れかけ／読んだ／未着手）と**次の期限**（◯日後）。
  決定9で決めた5語が、ここで初めて列の値として働く
- 並びの既定は「離れかけが先」。席で畳める
- 状態と期限の文字列は**純関数**に出してテストする（DOM が無いため）

- 入れるか、入れないか
- 入れるなら、段6として段5の後か、もっと先送りか
